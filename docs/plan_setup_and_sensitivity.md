## B. 실험

비용 표기: [표] 이미 있는 결과를 표·그림으로, [재현] 디코딩 결과를 다시 쓰는 CPU 계산, [GPU] 실시간 실행이나 새 디코딩.

### E1. 무선 장치와 GPU 사이 거리 (프런트홀) — 새 실험

모델:

- 편도 지연은 t = 5 µs/km × d이다. 스위치 지연은 등급표에서 고정값 하나를 더한다.
- 상향 샘플은 t만큼 늦게 서버에 도착한다. 그래서 L1 결과는 1.4 + t ms이다.
- 하향 grant는 무선 장치에 공중 송신 시각 전에 도착해야 한다. 그래서 서버는 t만큼 일찍 보내야 하고, 선행 시간은 4.0 + t ms가 된다.
- 결과적으로 복구에 쓸 수 있는 시간이 2t만큼 줄어든다. 서버 도착 기준 복구 마감은 11.0 − 2t ms이다.

거리:

| 거리 | 2t | 서버 도착 기준 마감 | 해당 배치 |
|---|---|---|---|
| 0 km | 0 | 11.0 ms | 같은 곳(edge) |
| 10 km | 0.1 ms | 10.9 ms | |
| 20 km | 0.2 ms | 10.8 ms | 흔한 7.2x 범위(확인) |
| 40 km | 0.4 ms | 10.6 ms | 중앙 집중 AI-RAN |
| 80 km | 0.8 ms | 10.2 ms | 중앙 집중 AI-RAN |

이론상 한계도 적는다. L1 결과부터 마감까지 남는 3.7 ms(11.0 − 1.4 − 5.9)가 2t를 넘으면 안 된다. 따라서 t ≤ 1.85 ms이고, 광섬유로 약 370 km이다.

- **E1a [재현]**: harq_latency.py에 --l1 1.4+t, --lead 4.0+t, --deadline 11.0−t를 주고, 거리별 재전송 감소, 지연 없이 기다릴 수 있는 창, 시간별 전달 비율을 계산한다. CPU 수 분.
- **E1b [GPU]**: 실시간 실행(n16_runtime 설정)을 --rescue-deadline-ms 11.0, 10.8, 10.6, 10.2로 돌린다.
  - 4셀과 8셀(서버 효과에 쓴 밀도)에서 거절 비율, 제시간 복구 비율, L1 늦음을 잰다.
  - 기존 방식은 거리와 무관하다(L1은 같은 양만큼 밀릴 뿐). 그래서 Reverb만 돌린다. 마감 4개 × 셀 2개 = 8실행이다.
- 그림: 거리에 따른 재전송 감소와 제시간 복구 비율. 원고 위치는 5.6 끝이나 5.4 지연 절.

### E2. TDD 패턴 [재현]

- harq_latency.py에 DDDSUUDDDD(DDDDDDDSUU와 같은 구조)가 이미 있다. 예전 출력(n7_*)에는 두 패턴이 모두 들어 있다.
- 현재 대표 실험(3.5 GHz, f35, 현재 정책)으로 다시 계산하고, 패턴별 재전송 감소와 지연을 표로 만든다.
- 상향이 많은 패턴(DSUUU)은 선택이다. PATTERNS에 줄 하나만 더하면 된다.
- 근거: 내부 분석에서 지연 없이 기다릴 수 있는 창이 DDDSU에서 2.1 ms, DDDDDDDSUU에서 2.6–4.1 ms이다.

### E3. grant 선행 시간 [재현]

- 선행 시간 1.5(Aerial의 3슬롯), 2, 3, 4, 5, 6 ms에서 복구 마감은 재전송 슬롯에서 선행 시간을 뺀 값이다.
- 재전송 감소와 지연 없이 기다릴 수 있는 창을 계산한다. review_analyses.py에 창 계산이 이미 있고, 예전 n7 출력에는 2, 4, 6 ms가 있다.
- 선행 시간이 바뀌면 실시간 실행의 마감도 바뀐다. E1b의 마감 실행이 같은 범위를 덮는다(10.2–11.0 ms). 더 짧은 마감(예: 선행 6 ms → 9.0 ms)이 필요하면 E1b에 실행 2개를 더한다.

### E4. L1 마감 판정 4.0 ms [표, 필요하면 GPU]

- 실시간 실행이 TB별 L1 완료 시각을 남기면, 3.0, 3.5, 4.0, 5.0 ms 기준으로 늦은 비율을 다시 센다.
- 남기지 않으면 E1b 실행에 기록을 켜서 같이 얻는다.
- 원고에 쓸 문장: L1 마감은 하드웨어가 아니라 L2 스케줄이 정하므로 전용 하드웨어와 AI-RAN에 똑같이 적용된다. Reverb는 L1 늦음을 최대 0.04%에서 0.08%로만 바꾸고, 복구를 둘씩 동시에 돌리면 최대 45.6%가 된다. 원고에 이미 있는 측정값이다.

### E5. 링크 적응 목표 (실패 확률이 너무 높다) [재현 + GPU]

이미 있는 것:

- olla.py 결과(n6_uma_v3_f35_olla)에 목표 1%, 3%, 10%가 있다.
- Reverb의 goodput은 기존 방식의 1.06, 1.31, 1.31배이다.
- 다만 목표 1%와 3%에서는 기존 수신기의 평균 MCS가 10.0으로 사다리 바닥에 붙는다.
- 그래서 첫 전송 실패가 5.8–5.9%에 머물고 목표에 닿지 못한다.

할 일:

- **E5a [GPU]**: MCS 사다리를 4–16으로 넓힌다. 같은 채널로 MCS 4–9 트레이스를 새로 만들고 디코딩한다(기존 방식, 큰 NRx).
- **E5b [재현]**: 목표 1%, 3%, 5%, 10%, 20%에서 goodput, 재전송, 잔여 손실, 평균 MCS를 계산한다.
- 선택 **E5c [GPU]**: 실시간 닫힌 루프(n25)를 목표 5%, 20%로 돌린다. 지금은 10%뿐이다.

원고:

- 대표 결과를 링크 적응 목표 10%(기존 수신기의 첫 전송 실패 10.2%, 상용망 7–10%와 같은 범위)에서 먼저 보인다.
- MCS 14 고정 실험은 부하가 큰 조건으로 둔다.
- 목표별 그림을 하나 넣는다.

### E6. MCS 14 고정 실험의 Eb/No별 실패율 [표]

- 대표 실험의 Eb/No 점별 첫 전송 실패율과 재전송 감소를 표로 낸다.
- 실패 10% 근처의 점에서도 효과가 같은지 보인다. 새 실행은 없다.

### E7. 안테나·사용자 수 (U3s, 진행 중) [GPU]

- 4 RX와 8 RX에서 1–4명일 때 기존 수신기, LMMSE K-best, NRx, 상한을 비교한다(plan_nrx_scale.md 3절).
- 8 RX NRx 평가가 진행 중이다. 변형 c는 queue_b, d는 main queue에 있다.
